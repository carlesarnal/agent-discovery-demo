The A2A Protocol

OpenAPI for AI agents

  • Agent Cards — structured capability declarations
  • Skills — typed input/output modes
  • Capabilities — streaming, batch, push notifications
  • Discovery — /.well-known/agent.json

But well-known requires knowing the host first.

Registry-backed discovery lets you query by capability.

// A2A Agent Card
{
  "name": "Summarizer Agent",
  "url": "https://agents.internal/summarizer",
  "version": "1.0.0",
  "capabilities": { "streaming": true },
  "skills": [{
    "id": "summarize-text",
    "name": "Text Summarization",
    "inputModes": ["text"],
    "outputModes": ["text"]
  }]
}

Step 2

Prompt template governance

./scripts/02-register-prompts.sh

Version 1

"variables": {
  "max_sentences": { "default": 3 },
  "input_text":    { "required": true }
}

Version 2 compatible

"variables": {
  "max_sentences": { "default": 3 },
  "input_text":    { "required": true },
  "tone":          { "default": "neutral" }
}

Adding an optional variable with a default is backward compatible.
Existing agents won't break — the same rule as adding an optional field to an OpenAPI schema.

Step 3

Breaking change rejected

./scripts/05-breaking-change.sh

What changed

Renamed input_text → content

Removed a required variable

Result

HTTP 409 — Rejected

BACKWARD compatibility violation

The registry catches this before production, not after.
Same rule as OpenAPI — you can't remove a required field from a backward-compatible schema.

Why This Matters

Discovery approaches, compatibility rules, and the standards ecosystem

Discovery

Why registry-based agent discovery?

ApproachWhat it doesLimitation
Hardcoded URLsDirect agent-to-agent callsBreaks when endpoints change
DNS / Service meshDiscovers services by hostnameDiscovers services, not capabilities
A2A well-knownCapabilities at /.well-known/agent.jsonRequires knowing the host first
Registry-backedQuery by capability, skill, I/O modeCentralized dependency

Same evolution as API discovery: from hardcoded URLs → to API gateways → to OpenAPI-driven catalogs.

Compatibility

Same rules as OpenAPI schema evolution

ChangeOpenAPI schemaPrompt template
Add optional field (with default)CompatibleCompatible
Remove required fieldBreakingBreaking
Rename a fieldBreakingBreaking
Change field typeBreakingBreaking
Add new endpoint / skillCompatibleCompatible

The governance pattern is identical. Same registry, same rules, new artifact types.

04

Going to Production

What you'd add beyond the demo

Production Hardening

From demo to deployment

Automated registration

Agents register on startup via sidecar or init container. Deregister on shutdown. No manual scripts.

Health-aware discovery

Combine with Kubernetes health checks. Registry returns only healthy agents. Dead agents are pruned.

Schema evolution strategy

Define compatibility modes per group. Enforce in CI/CD — reject incompatible changes before merge.

Multi-tenancy

Registry groups isolate agent namespaces per team. Same pattern as separating OpenAPI specs per domain.

Takeaways

Four things to remember

01

The open standards arc continues. OpenAPI → AsyncAPI → A2A. Each generation standardized interface descriptions for its domain.

02

Agent Cards are OpenAPI for agents. Structured capability declarations — versioned, discoverable, and machine-readable.

03

Prompt templates need governance. The same version control and compatibility rules you apply to API specs — not optional for AI.

04

The tooling already exists. Apicurio Registry — one CNCF sandbox project for OpenAPI, AsyncAPI, Avro, Protobuf, and now A2A.
